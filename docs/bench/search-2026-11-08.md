# Chat search: index and query timings (2026-11-08)

**What it is:** measured numbers for the transcript search index (`crates/core/src/search`).
**How:** `cargo run --release -p atlas-core --example search_bench -- --projects <dir> --config <dir> --data <scratch>`.
Release build, Windows 11, one machine, the real `~/.claude/projects` (read-only). The index went to a scratch folder. The bench prints counts and timings only, never transcript text.

## Data

- 1,896 transcript files, 5.48 GB on disk.
- 28,339 searchable messages (user and assistant text only; tool results, tool input, thinking and meta lines are not indexed, which is why 5.5 GB of JSONL becomes ~70 MB).

## Build and size

| Measure | Result | Budget (design note) |
|---|---|---|
| Initial build, OS file cache cold-ish (first run of the day) | 26.1 s | 60 s |
| Initial build, files already in the OS cache | 5.9 s | 60 s |
| Index size on disk (db + WAL) | 70.9 MB | reported, no budget |
| Peak working set during build | 88 MB | about the usage indexer plus one batch |
| Pass with nothing changed (stat 1,896 files, read none) | 23-26 ms | 300 ms |
| Incremental pass, 5 newest chats, last ~256 KB of each re-read | 33 ms (the pass only; add the 300 ms debounce) | 1.5 s after the usage change event |

The build runs on one thread at below-normal priority and never touches the usage cache. Offsets and rows commit in one transaction, so stopping mid-build loses nothing (tested with 60,000 synthetic messages).

## Queries (limit 20, warm connection, 15 runs each)

| Class | Queries | p50 | p95 | max |
|---|---|---|---|---|
| 1 word | 12 | 3.7 ms | 6.6 ms | 7.5 ms |
| 3 words (all must match) | 8 | 3.5 ms | 4.9 ms | 5.4 ms |
| Quoted phrase | 6 | 0.8 ms | 2.0 ms | 2.1 ms |
| Very common words ("the", "to the", "and") | 3 | 18.2 ms | 20.9 ms | 21.8 ms |
| Word not in the index | 3 | 0.0 ms | 0.1 ms | 0.1 ms |
| First run of each query (cold page cache) | 32 | 3.0 ms | 17.6 ms | 19.7 ms |
| Search-as-you-type (every prefix of 3 words) | 28 | 0.7 ms | 4.9 ms | 6.0 ms |

Budget is p95 50 ms for 1 word, 3 words and phrase; every class, including the very common words, is under it.

## What the first run found (kept for the record)

The first version of the bench, with SQLite's own `snippet()`, measured the very common word at p50 85 ms and typing at p95 337 ms. Cause: `snippet()` re-walks the posting lists of every query term for each of the 20 returned rows, and a prefix like `p*` expands to thousands of words (80-340 ms for 20 rows; the ranking query itself was 12-45 ms). Fix: step 2 now reads the 20 message texts by id and builds the snippet in Rust (constant time), and a last word of one or two letters is a whole-word match until the third letter is typed. Same data, same machine, numbers above are after the fix.

## Caveats

- One machine, one data set; a much larger history will scale ranking time with the number of messages that match a very common word.
- Messages repeated across resumed sessions are kept once (first file indexed wins); the usage ingest saw no repeats on this data.
- Ranking is bm25, so a short message with the word ranks above a long one with it many times; recency breaks ties.
