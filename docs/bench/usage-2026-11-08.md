# Usage engine bench, 2026-11-08

Harness: `cargo run --release -p atlas-core --example usage_bench` (release build, Will's PC,
16 logical cores, Windows 11). Two runs are merged below: the real-data run and the synthetic
run. Real-data numbers come from the real Claude projects folder, opened read-only, with the
cache in a scratch folder outside it. No message text is stored in the cache, the report or
this file.

Commands:

```
usage_bench --projects C:/Users/Will/.claude/projects --data <scratch> --runs 3 --out real.md
usage_bench --data <scratch> --gen-huge --append-test --synth 1000000 --out synth.md
```

## Real data (5,872 files, 5.51 GB; 1,890 session files tracked; 113,051 messages)

| Metric | Budget | Measured | Result |
|---|---|---|---|
| First full index, OS cache warm | <= 30 s | median 18.8 s of 3 (18.8, 19.3, 17.0 s) | PASS |
| First full index, cold cache | <= 90 s | not measured: the OS file cache cannot be flushed without a reboot or an elevated tool | NOT MEASURED |
| Indexer peak working set during a full index | <= 250 MB | 38 MB (whole process, after 3 full indexes) | PASS |
| No-change rescan (stat all files, zero bytes parsed) | <= 300 ms | median 18 ms, max 19 ms over 6 rescans | PASS |
| No-change rescan reads only appended bytes | <= bytes the files grew | 2,469 bytes read, files grew 2,469 bytes (a running Claude Code appended while measuring) | PASS |
| `usage_dashboard` | <= 50 ms | median 1.4 ms, max 1.8 ms | PASS |
| `usage_timeline` 365 d x day | <= 50 ms | median 1.5 ms, max 1.8 ms | PASS |
| `usage_timeline` 365 d x day, by model | <= 50 ms | median 1.7 ms, max 1.8 ms | PASS |
| `sessions_list` page of 50, worst of 4 sorts x 2 directions | <= 50 ms | worst = tokens desc, median 1.2 ms, max 1.4 ms | PASS |
| `session_detail`, largest session (14,397 messages) | <= 100 ms | median 45.4 ms, max 48.9 ms | PASS |
| Read-only proof: size + mtime listing of `projects/` before and after | no change | 5,872 files listed; 2 grew, 0 added, 0 removed, 0 shrank, 0 rewritten at the same size | PASS (live growth) |

An earlier run of the same command gave 35.8 s, 15.6 s and 16.2 s (the first pass was slow;
the cause was not established, an OS cache that was not yet warm is the likely one). The run
in the table is the later one. The budget is judged on the median; the 35.8 s outlier is
listed here because it exceeded 30 s.

"2 grew": files belonging to live Claude Code sessions were appended to while the bench
ran. Atlas did not write them: the bench opens nothing under
`projects/` for writing, and the engine's code under `crates/core/src/usage/` has no write,
create, rename or remove call (acceptance 20).

An earlier version of the harness failed the "reads zero bytes" row on the real folder
because live sessions had grown between the index and the rescan. The row now compares bytes
read with bytes grown in the window (equal here), and still requires exactly zero when
nothing grew (the synthetic tree and the fixtures).

## Synthetic (generated at bench time)

| Metric | Budget | Measured | Result |
|---|---|---|---|
| Synthetic 300 MB single file, full parse | <= 6 s | 300 MB, 6,759 messages: 116 ms (median of 3: 121, 115, 116) | PASS |
| A 300 MB file adds <= 32 MB peak working set over a 1 MB file | <= 32 MB | 1 MB file peak 8 MB; 300 MB file peak 15 MB; delta 6.3 MB | PASS |
| Append on disk -> `changed` event | <= 1000 ms | 507, 508, 509, 507, 508 ms over 5 appends of about 60 KB (500 ms debounce included) | PASS |
| One append of <= 64 KB -> DB commit, after the debounce | <= 50 ms | worst 9 ms past the debounce | PASS |
| `usage_dashboard` (1M messages) | <= 50 ms | median 11.5 ms, max 12.1 ms | PASS |
| `usage_timeline` 365 d x day (1M) | <= 50 ms | median 10.3 ms, max 10.3 ms | PASS |
| `usage_timeline` 365 d x day, by model (1M) | <= 50 ms | median 10.7 ms, max 11.1 ms | PASS |
| `sessions_list` page of 50, worst of 4 sorts x 2 directions (1M) | <= 50 ms | worst = cost desc, median 19.0 ms, max 21.6 ms | PASS |
| `session_detail`, largest session (20,000 messages) (1M) | <= 100 ms | median 62.5 ms, max 233.0 ms on the first run (other builds were running), 69.2 ms and 99.2 ms on two reruns; close to the budget, no headroom | PASS (reruns) |

- The 300 MB file is shaped like a long session: one assistant line to every three 14 KB
  tool-result lines (about 44 KB per message), so 116 ms says the skip path for big
  non-usage lines is fast; it is not a claim about 300 MB of dense usage lines. The real-data
  index above (5.5 GB in about 18 s) covers real line mixes.
- 1M-message cache: 1,000,000 messages, 5,001 sessions, built by the real pipeline in 51.6 s,
  cache file 430 MB. The spec sets no budget for this build; reported as measured. The real
  cache for the 113,051 messages above is far smaller.

## Notes

- The dashboard went from 2.2 ms to about 12 ms when the card session counts changed from
  "sessions started in the period" to "sessions with a message in the period" (an indexed
  EXISTS probe per candidate session). Still far under 50 ms. The timeline keeps "started"
  and is labelled so.

- Estimate vs Claude Code's own `cost-state` figure (report only, no threshold, Q5):
  224 sessions, 1 with unpriced tokens; median deviation 0.00 %, 132 sessions within 2 %,
  mean signed deviation +22.94 % (Atlas higher), worst 3270 %. Not explained: the worst cases
  are probably sessions where the file holds more than the session Claude Code costed
  (resumes, compaction), but this was not checked. Every cost in the app is labelled
  "estimate" (Q5).
- Real data shape: 1,890 session files tracked (0 missing), 1 malformed line, 0 lines over the
  64 MiB cap, 739 cross-file duplicate messages, 0 rows with an assumed 5m cache write,
  1 unknown model.
- Cold-cache first index was not measured.
